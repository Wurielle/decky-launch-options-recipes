# DLOR OptiScaler

A self-contained OptiScaler installer recipe. No OptiScaler, driver, SDK, or plugin binaries are stored in this repository. Enabling the main option downloads and verifies the selected components, discovers the selected game's rendering directory, installs the files, and declares the fixed DXGI Wine override through DLO's normal environment handling. Disabling it restores originals and removes only unchanged recipe-owned files.

## Options

Nightly configuration controls, including FSR4 model/GPU support and XeFG/DLSSG MFG, are available in the separate [OptiScaler settings recipe](../optiscaler/README.md). Import the wanted settings alongside this installer, not the separate fgmod launcher. The existing Nightly Upgrade option is compatible and explicitly opts the core into latest resolution. Unselected dropdowns preserve the INI; selected settings are explicit environment overrides.

- **DLOR OptiScaler:** install/manage when enabled; uninstall when disabled.
- **Core:** the manifest-pinned official nightly from `optiscaler/OptiScaler-nightly`, using its newer supporting-DLL directory layout. There is no stable-core selector or flat 0.9 package fallback; stale release-channel environment settings cannot select stable.
- **Injection proxy:** fixed `dxgi.dll`, paired with `WINEDLLOVERRIDES="dxgi=n,b"` in the ON option. There is no automatic proxy selection or proxy dropdown. An occupied foreign DXGI proxy is refused rather than silently replaced or switched to another proxy.
- **OptiPatcher:** mandatory in the main install, pinned to the official `optiscaler/OptiPatcher` versioned stable release in the JSON manifest (currently `v0.42`, source `OptiPatcher_v0.42.asi`), installed as `OptiPatcher.asi`, using its full SHA256 and the existing cache. Installs into the resolved ASI plugin directory and defaults only `[Plugins] LoadAsiPlugins=true`; an explicit user environment override can select `false`. The retired optional checkbox is removed; stale `DLOR_OPTISCALER_OPTIPATCHER=0` cannot disable this component. OptiPatcher only supports the games/versions documented upstream; it does not universally add DLSS inputs.
- **FSR4 compatibility (third-party):** the bundled official SDK is the default. Explicit alternatives use the Framegen author's `xXJSONDeruloXx/OptiScaler-Bleeding-Edge` mirror:
  - `rdna23-int8`: the mirror's FSR4.0.2c compatibility upscaler.
  - `rdna34-official-411`: the mirror's FSR4.1.1 driver override. The source is still a third-party mirror, despite the profile's historical identifier.
  - `rdna2-valve-411`: experimental Valve/RDNA2 driver pair. Supplies files only, retaining the nightly injector; it does not change `Fsr4GpuSupport` or `LoadCustomAmdxc64OnRdna2`.

The nightly already includes Nukem’s `OptiScaler/dlssg_to_fsr3_amd_is_better.dll` and integrated FakeNVAPI (`[fakenvapi] UseFakenvapi=auto`, upstream default true). No separate legacy FakeNVAPI DLL or older injector is added. This recipe does not force frame-generation settings or claim Framegen parity. Explicit user environment settings are supported as described below.

Every dropdown's **None** entry leaves explicit user environment policy untouched. Third-party profiles are file choices only: their files are not guaranteed to be activated under the preserved user/upstream configuration. Do not run multiple independent OptiScaler installers against the same game; remove the legacy fgmod installation option when replacing it with this recipe.

## Downloads and integrity

The checked-in [`scripts/downloads.json`](scripts/downloads.json) explicitly pins the exact URLs, SHA256, sizes, repositories, tags and names of all nine external binary downloads: official nightly core, mandatory official versioned stable OptiPatcher, the three named FSR profiles (including both RDNA2 DLLs), and conditional official Linux x64/arm64/x86 7zip consoles. Ordinary installation does not query mutable release metadata. These pins were selected from official GitHub release metadata and verified against complete downloaded bytes. Missing, unsupported, or mismatched digests abort preparation before game files are changed. Each archive, raw optional DLL/ASI, cached archive, and cached extracted package is verified before use. Release provenance and file ownership are kept in the private per-game journal.

GitHub-provided hashes establish agreement with the GitHub-hosted release. They are **not publisher signatures, a malware scan, proof of AMD endorsement, or a guarantee that an experimental driver works on a particular GPU**. Third-party profiles are opt-in. Never use graphics injection mods in an anti-cheat-protected online game without that game's explicit permission.

Caches live under `~/.dlor/cache/dlor-optiscaler/`; journals/backups under `~/.dlor/state/dlor-optiscaler/`. Normal installs use the JSON pins regardless of metadata-cache age. With **OptiScaler Nightly Upgrade** enabled, the core requests a fresh official nightly response on every enabled launch, bypassing metadata TTL and refusing stale/offline fallback. A fresh complete upstream `sha256:` digest is mandatory; unavailable/invalid metadata fails closed while the stock runner continues the game. Other components, including the named FSR 4.1.1 profiles, remain pinned. Valid extracted files are reused; corrupted/incomplete preparation is rebuilt. Uninstall does not resolve release metadata or download mod payloads, and reusable download caches remain.

ZIP, supported tar formats, and 7z/BCJ2 are handled without running upstream setup scripts. If no compatible native 7zip console exists, an official `ip7z/7zip` console is downloaded, SHA-verified, and cached privately. No sudo, global pip installation, desktop dialogs, or system package changes are used. Archive traversal, links, devices, privileged modes, ambiguous Windows paths, and size/count overflows are rejected.

## Placement and restoration

Discovery stays inside `STEAM_COMPAT_INSTALL_PATH`. It searches case-insensitively for existing `OptiScaler.ini` anchors, then uses bounded AMD64 PE imports and generic shipping-executable evidence. The normal helper receives the installation root, not the original game's command arguments. It does not maintain a list of game names or fixed candidate directories. Ambiguous cases fail without guessing; `DLOR_OPTISCALER_EXECUTABLE` is an optional advanced disambiguation override.

The archive's directory structure and INI contract determine placement. In the v10 nightly the injector/INI remain beside the renderer, while supporting DLLs remain under `OptiScaler/`, including its D3D12 subtree. Existing `Libraries.OptiDllPath`, supported per-library overrides, and `Plugins.Path` are respected within the selected game. Unresolvable drives or paths outside that game are refused. Custom paths are never persisted as normalized absolute paths. Relative per-library/plugin paths use the validated inherited launch CWD; an outside-game, ambiguous, symlinked, quoted, or otherwise unresolvable path is refused rather than repaired. A later different CWD is not made equivalent by rewriting configuration.

Without explicit environment overrides, the only production INI setting changed or restored is `[Plugins] LoadAsiPlugins`. Other settings—including FG, FSR, FakeNVAPI, fonts and custom paths—remain intact; no profiles force configuration presets. A new INI comes from upstream with only ASI loading enabled.

### Explicit environment-to-INI settings

The physical `scripts/update_optiscaler_config.py` ports the user's [Decky-Framegen updater contribution](https://github.com/xXJSONDeruloXx/Decky-Framegen/blob/main/defaults/assets/update-optiscaler-config.py), retaining its BSD-3-Clause attribution. It is distributed and SHA-verified with this recipe, not fetched from Framegen at runtime. The three familiar environment formats target **existing, case-sensitive keys**:

- `OptiScaler_Section_Key=value`, for example `OptiScaler_Plugins_LoadAsiPlugins=false`.
- `Section_Key=value`, for example `Plugins_LoadAsiPlugins=false`.
- `Key=value`, only when that exact key occurs in exactly one section.

Sections may use their exact spelling or omit `-` and `.`, so `OptiScaler_VSync_Key` and `VSync_Key` target `[V-Sync] Key`. Deterministic priority is **full OptiScaler prefix > section prefix > unique bare key**, independent of environment enumeration order. Conflicting equal-priority aliases and ambiguous normalized section/key matches are refused; unknown keys and ambiguous bare keys are ignored. `PATH` and `Path` remain distinct. Use ordinary DLO environment assignments; no new UI selector or plugin/runner change is needed. Prefer the full prefix to avoid accidental collisions with unrelated ambient variables.

Overrides are resolved against the existing INI, or the verified upstream template for a new installation, **before** library/plugin placement. The same effective bytes are checked under the installation lock and committed through the ownership transaction. Unsafe/outside-game/symlinked/ambiguous paths are still refused, not repaired. An explicit `LoadAsiPlugins=false` wins over the default and disables ASI loading, including OptiPatcher; it does not omit the mandatory ASI file.

Each selected value is one literal native INI right-hand side: backslashes, `$`, `%`, `#` and `;` are not regex replacements, interpolation or shell code. CR, LF and NUL are refused. Unrelated lines/comments, UTF-8 BOM, CRLF, final-newline state and current INI permissions are retained. The targeted old right-hand side is displaced in full (including any inline suffix) and recorded for exact restoration; place persistent comments on their own lines. The standalone compatibility function `update_optiscaler_config(file_path)` is available, but the installer reuses pure resolution/rendering and never invokes that unmanaged writer after installation. Values are not dumped to logs.

An active override is a fresh request on **every install/launch**. If an overlay/user edited that same setting, the explicit value wins again and the latest displaced user line becomes its restoration baseline. Untargeted owned-setting guards remain unchanged. On removing an environment assignment, the next enabled launch restores its prior owned line only if the current value still matches the recipe's last value; OFF does the same. Later foreign edits are retained. This reversible DLO lifecycle deliberately differs from Framegen's original unmanaged persistent writer. Equal pre-existing values do not grant restoration/removal ownership. Private journals/backups necessarily contain the selected INI values; logs do not print them.

Old journals relinquish ownership of non-ASI settings without restoring their old values. This protection is sticky across updates: even an exact old installed hash cannot authorize whole-file restore/removal of those retained bytes. OFF applies the same migration without requiring a prior new ON. An unfinished legacy transaction involving an INI is refused before recovery writes; its current files, journal and backups remain for review. New transactions distinguish ASI-only operations from explicit-environment operations. Environment transactions record their exact key allowlist and retired owned overrides; recovery replays those narrow operations against the verified previous backup and checks the resulting digest before any rollback writes. A broad environment marker cannot authorize unrelated setting restoration. Unrelated file ownership/backups are unchanged.

Original files are backed up before replacement, with a durable transaction journal for interrupted updates. Equal pre-existing files are not acquired as removal-owned files. Modified external files are preserved, and originals whose restoration is blocked retain retryable ownership. No broad-name upstream uninstaller is invoked. Preparation failures do not prevent the original game command from running.

## Entry points and runner contract

The main toggle uses the existing two-argument `remoteScript` helper to call commit-pinned `install.sh` and `uninstall.sh` through the unchanged helper-only `~/.dlor/run`. There is no inline launcher/bootstrap, wrapper mode, HelixSR dependency, plugin update, or shared runner/schema change. Other ordinary helper recipes can run before or after these calls.

The generated ON/OFF fields contain only ordinary environment assignments and the file-backed runner invocation. ON declares `WINEDLLOVERRIDES="dxgi=n,b"`; OFF adds no Wine override. DLO performs its normal delimiter-based merge with other **DLO-managed** Wine assignments. This does not merge arbitrary ambient Wine settings or return a success-gated setting from the installer: the ON declaration remains applied even when preparation or downloading fails. The stock runner reports helper failure and still executes the original game command; continuation is not proof of successful preparation or working DLL loading.

Both calls also declare `DLOR_OPTISCALER_ACTION="install"` or `"uninstall"`, and supply full Git revision/repository context as `DLOR_OPTISCALER_SOURCE_REVISION` and `DLOR_OPTISCALER_SOURCE_REPOSITORY`, because the installed runner does not export `DLOR_SCRIPT_REVISION`. These namespaced values do not overwrite another helper's shared revision context. The existing helper retains its standard `DLOR_REPOSITORY` assignment when building for a fork.

The outer shell entrypoints retain the ordinary DLOR trust boundary: the unchanged runner fetches complete commit-pinned HTTPS scripts. They intentionally have no self-hashes in the JSON, avoiding a self-hash cycle. The generated shells contain only a `MANIFEST_SHA256` trust anchor, never artifact or module digest literals. Each shell authenticates a private snapshot of `scripts/downloads.json`, builtin-extracts its canonical `loader.py` digest, then authenticates a private loader snapshot. Both snapshots are read-only. The physical loader rechecks the JSON SHA before parsing it and compiles the complete SHA-verified runtime module bytes directly, ignoring all `.pyc` files. The JSON runtime map includes `loader.py`, `installer.py`, `artifacts.py`, `game_discovery.py`, `update_optiscaler_config.py` and the legacy-only `nightly.py`; normal ON/OFF need not download the legacy module. All source URLs are derived from the validated source repository/full revision and these recipe-local filenames. A corrupt cache must be repaired before use. Downloads are bounded HTTPS-only curl with EOF stdin; same-cache-filesystem rename publishes verified bytes. HOME is canonicalized before constructing the private source cache, accepting legitimate HOME-ancestor symlinks while rejecting internal cache links.

Direct administrative invocation of install/uninstall requires the same full `DLOR_OPTISCALER_SOURCE_REVISION` (or `DLOR_SCRIPT_REVISION`) context; normal toggling supplies it automatically. The cached loader, Python modules, and verified payloads can be reused offline, but **the stock runner still downloads the outer shell entrypoint on every launch**. A fully offline launch therefore continues the game without running a freshly acquired helper.

Each entry logs separately under `~/.dlor/logs/dlor-optiscaler/install/` or `uninstall/`, retaining ten regular log files per entry; the stock runner also maintains its own `~/.dlor/logs/run/` logs. Logging is best-effort. Auxiliary host cleanup and recipe logging stay within the helper, preserving the game's argv, stdin, inherited descriptors, environment (apart from declared DLO assignments), and exit status. No recipe-local wrapper cancellation guarantees are added to the unchanged runner. The shell bootstrap kills/reaps only its exact loader downloader and removes its own private work directory when that bootstrap receives SIGINT/SIGTERM. The Python module source loader retains cancellation of its own auxiliary download when the loader receives a signal. Neither contract adds parent-only cancellation guarantees to the stock runner.

### Compatible Nightly Upgrade

The existing **OptiScaler Nightly Upgrade** option retains ID `optiscaler-nightly-upgrade`, its name, priority `-1`, and empty OFF. Its ordinary `DLOR_OPTISCALER_LATEST="1"` assignment makes the main DLOR ON perform the fresh core lookup inside its normal ownership transaction. The later separate helper no-ops whenever the main ON or OFF action is present: OFF plus Nightly ON cannot reinstall, even after a main-helper failure. The helper carries its own namespaced source revision/repository so nested runner contexts do not substitute another recipe's module revision.

Nightly alone against a valid existing DLOR journal requires an unchanged owned proxy, retains the installed third-party profile unless explicitly overridden, and uses the same transaction/backups/config policy as main ON. Ownership is rechecked under the final write lock, so a concurrent OFF cannot become a fresh install. An empty DLOR journal is a no-op, not an invitation to run legacy copy logic. No fgmod DLL or overlay is copied into a DLOR-managed tree. After disabling Nightly Upgrade, the next ordinary main ON uses the pinned core again.

Only a game with no DLOR journal can take the physical legacy fgmod updater path. It preserves the existing selected variant, supporting-DLL precedence, case-aware modern/flat layout, INI bytes, `OPTISCALER_CACHE_DIR` override and default temporary cache. It always fetches latest official core metadata, verifies archive SHA/size before extraction, and verifies extracted-cache inventories before reuse. It does not execute setup or DLLs. Do not use the separate legacy Install/Uninstall actions to manage a DLOR-owned game.

### Updating pins and runtime sources

Update exact asset descriptors in `scripts/downloads.json` after checking the intended official/versioned release and rehashing the complete downloaded bytes. Keep named FSR 4.1.1 selections on their selected tags; do not silently substitute a different driver release. Prefer versioned stable OptiPatcher URLs, not mutable `rolling` assets. If an upstream URL's bytes change, old pins deliberately fail closed until explicitly reviewed/updated; never accept a fresh hash for mismatched bytes automatically.

After editing pins, a runtime module, `loader.py`, or the shell generator, run `python3 -I -B recipes/dlor-optiscaler/scripts/update-source-hashes.py`. It preserves external download descriptors, regenerates the JSON runtime hashes, computes the JSON trust anchor, and regenerates main install/uninstall plus the existing OptiScaler Nightly Upgrade shell. It prints `runtime` and `MANIFEST_SHA256`, does not embed a module-hash dictionary in Python, and does not touch `index.ts`, shared runner/schema or `recipes.json`. Commit all resulting source files together; publication/catalog generation is a separate normal pinned-source build. Old imported options must be re-imported to acquire the new immutable source revision.

## Validation boundary

The actual official `nightly-20261024` archive (`OptiScaler_v10.0.0-pre1_20261024.7z`) was downloaded and matched to GitHub SHA256 `74f20189e0ec76288c86d69057b3feb4750f4680118a9852fb743b343274ac1d`. Filesystem tests installed, reinstalled, checked all 18 files, and uninstalled this real payload in a disposable nested game tree without executing its DLLs or setup scripts.

Offline tests also use explicitly synthetic PE/SDK fixtures for discovery, corruption, rollback, config ownership, source verification, and game-command handoff. Launcher tests execute the real DLO parser at commit `a3996e590b61f0a985a0182cb89278a4850e39f6` and the backend-installed, unchanged helper-only runner against harmless game/installer fixtures. To run them, set `DLO_CONSUMER_SOURCE` to a directory containing that revision's unmodified `run.py` and `shared.py`; their SHA256 values are checked. Run `python3 -I -B -m unittest discover -s recipes/dlor-optiscaler/tests -p 'test_*.py' -v` with the repository's Node toolchain/dependencies available. Source transfers, including failed/partial responses, are local fixtures; no mod or game binary is executed by these tests. Coverage includes exact short ON/OFF strings, ON/OFF/failure continuation and declared Wine policy, other DLO-managed Wine assignments, quoted/space/Unicode paths, argv/stdin/descriptor preservation, cold/warm/corrupt source caches, partial-transfer cleanup, home/cache symlink boundaries, logging retention/fallback, and untrusted bytecode. It does not claim the removed bootstrap's acquisition or parent-only cancellation semantics.

These tests do not establish Steam Deck UI behavior, Wine DLL loading, GPU compatibility, image quality, frame generation, or performance. Real device/game validation remains necessary.
